# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A generator that builds a day-accurate historical dataset of Italian regions, UTS/provinces and municipalities from 1861-03-17 to today, from ISTAT SITUAS (source of truth) and ANPR (cross-check only), and keeps it updated via GitHub Actions. The published dataset is self-contained and agnostic about how and by whom it is used (D39): only the territories (`regions.json`, `provinces.json`, `municipalities.json` and their JSON Schemas).

**`docs/GENERATOR_IMPLEMENTATION_PLAN.md` is the specification and the roadmap.** Read the relevant sections before any change:

- Implement the steps of §12 **in order**; a step starts only when the previous one meets its acceptance criteria. When a step meets its acceptance criteria, mark its heading in §12 with `— DONE` (e.g. `### Step 1 — Scaffolding — DONE`).
- §1–§11 are the spec. If the implementation reveals a contradiction or an uncovered case, **stop and ask** instead of improvising. The decisions in §13 must not be changed without discussion.
- Invariants (§8) must be enforced by code, not by convention.

## Workflow and commits

- When asked for an implementation, **run `git pull` on the current branch before reading any code**, so you work on the up-to-date version.
- Every implementation happens on a **feature branch** created from `main` (never commit directly to `main`).
- When a step is finished, **ask the user before committing**.
- Before every commit that touches `docs/GENERATOR_IMPLEMENTATION_PLAN.md`, **show the user the full diff of the plan** (`git diff docs/GENERATOR_IMPLEMENTATION_PLAN.md`) and wait for approval. Paste the diff into the reply text as a `diff` block: tool output is not visible to the user.
- After finishing a step, remind the user to **start a new session** instead of continuing in the current one.
- Commit messages describe what was done (e.g. "Project scaffolding: …"), **never** the plan step (no "Step 1", "complete step N").

## Conventions that are not obvious

- **ESM + native TS**: relative imports use the `.ts` extension (`./config.ts`); `tsc` rewrites them to `.js` in `lib/` (`rewriteRelativeImportExtensions`). `erasableSyntaxOnly` is on: no `enum`, `namespace` or parameter properties.
- **`dist/` is the published dataset** (three entity files and their schemas); `reports/` holds the internal reports of the release (`variations.json`, `anomalies.json`, `changes.json`, `meta.json` with `data_version`), committed with the data but never published. Compiled code goes to `lib/` (ignored). Never point build output at `dist/`. `dist/`, `reports/` and `registry/` are committed. A change that alters `dist/` needs its CHANGELOG entry (`npm run release -- changelog`; `test.yml` runs `release -- check`). Licences: generator MIT (`LICENSE`), data CC BY 4.0 (`LICENSE-DATA`, the npm package's `LICENSE`).
- **Dates**: ISO `YYYY-MM-DD` strings, pure calendar arithmetic (no `Date` timezone logic). Internally half-open `[validFrom, validTo)`; the public JSON uses an inclusive `valid_until` — conversion only in the emitter (§4.1).
- **Line endings**: LF everywhere (`.gitattributes`, `.editorconfig`), except `test/fixtures/**`, which is `-text` and must stay byte-identical to the real API responses (the ANPR CSV is CRLF).
- Configuration lives in `src/config.ts` (zod schema with defaults from the plan; nested objects use `.prefault({})` so partial overrides still get inner defaults). `resolveConfig()` returns absolute paths.

## Architecture

Pipeline (§6): fetch → normalise → snapshot store → breakpoint calendar → snapshots + completeness bisection → internal crawl + identity graph → identity resolution → versions → variations & links → overrides → derived fields → ANPR cross-check → invariants → emit → changes. Each stage has its own directory under `src/` (layout in §14; empty directories hold a `.gitkeep` until their step is implemented).

- `src/cli.ts`: the §10.1 commands (`bootstrap`, `update`, `rebuild [--refetch]`, `audit [--samples N]`, `validate`, `diff <from> <to> [--out]`), implemented in `src/commands/`. `main(argv, io, config, clock, runtime)` is exported and testable; commands are declared in the `commands` table. The global `--today` flag is resolved here (flag → the command's `defaultToday` (offline `rebuild`: the `today` of `calendar.json`) → `dates.today` → current date in Europe/Rome) and passed to commands as `ctx.today` (and `ctx.config.dates.today`): build code never reads the clock. `defaultRuntime` (system clocks, fetch transport) is chosen here; tests pass their own `Runtime`. `test/unit/clock-usage.test.ts` enforces this (only `dates/calendar-date.ts`, `cli.ts`, the HTTP client/clock and `logger.ts` may read it).
- `src/http/` (§6.1): `transport.ts` is the `Transport` contract (unencoded URLs/bodies; connection failures must be thrown as `NetworkError`, anything else is treated as a bug and not retried). `fetch-transport.ts` is the real one and the only place requests are encoded (`encode.ts`, strict RFC 3986, including the report URL inside internal API bodies). `client.ts` (`HttpClient`) composes `adaptive-limiter.ts` (AIMD pool) and `token-bucket.ts` (both per host, derived from the URL), `backoff.ts`, `circuit-breaker.ts` (per family: `situas-public-snapshots`, `situas-public-reports`, `situas-internal`, `anpr`; opens after `circuitBreakerThreshold` failures of more than one request lasting `circuitBreakerMinFailureMs`, then requests wait for a single probe after a doubling cooldown; the family is lost for the run, `CircuitOpenError`, only after `circuitBreakerMaxOpenMs` of open time; a request out of attempts with no family success since its first failure waits for the verdict (`awaitVerdict`, one retry per `backoffMaxMs`, `request-held` event), a request failing alone gives up at the opening condition (`alone`), D38) and `cache.ts` (one atomic file per request; per-call policy `prefer` | `refresh` | `{ maxAgeDays }` | `{ fetchedSince }`, optional `staleFallback`). Time comes from an injectable `Clock`; tests use the virtual clock of `test/helpers/http.ts`. Adapters declare an `Endpoint` (`id`, `family`, `timeoutClass`, `decode`); `decode.ts` has the decoders, which throw `TransientResponseError` (retried, at most 2 extra attempts) or `ResponseValidationError` (permanent, disables that endpoint id for the run: later requests throw `EndpointDisabledError`). Permanent validation errors never touch AIMD or the circuit breaker and never trigger `staleFallback` (D26). The client reports through `onEvent` (`retry`, `changed`, `degraded`, …) and never decides anomaly severity.
- Internal API quirk: non-empty results are a JSON string containing the JSON (double-encoded); empty ones are `text/plain`. Always parse with `parseJsonBody`.
- `src/sources/` (§3, §6.2): `SituasPublicSource` (`fetchSnapshot`, `fetchEventList`, `fetchCount`; regime → `pfun` table and event code vocabularies in `situas-public/pfun.ts`), `SituasInternalSource` (r1–r9) and `AnprSource` (`fetchAnpr`, half-open dates, row issues, `AnprFormatError` for structural problems), wired by `createSources(client, config)`. Each endpoint's zod row schema normalises while validating (`normalise.ts`), so bad rows become `ResponseValidationError`. Field names are mapped explicitly per endpoint, never with generic fallbacks (D29; e.g. pfun 100 uses `COD_VARIAZIONE_M`). A `Stato estero` counterpart (only `AS`/`AN`/`CE`/`AQ`, `ABROAD_EVENT_CODES`) becomes `abroad: true` with `related: null`, never a territory to resolve (D31); r8 `Tipo Uts associato` may be blank only for it.
- `scripts/fixtures-fetch.ts` (`npm run fixtures:fetch [-- <fixture path>...]`): downloads the §11.2 fixtures through the client and writes bodies exactly as served plus their manifest entries. With paths, only those are recorded (a full run re-records the event lists and counts at the download date, i.e. new files).
- `src/store/` (§6.3): `Store` (snapshots, event lists, internal reports). Rows go to append-only, content-addressed `RowLog`s (`row-log.ts`, row hash = SHA-256 of `canonicalJson`); each stored response has a zod-validated manifest (`manifest.ts`) with sorted `row_hashes`, `content_hash` (of the row hashes only), `adapter_stats` (outside the hash), `history` and `projection_version` (`projection-versions.ts`: bump an entry whenever an adapter changes its projection; manifests of another version are ignored, D32). Same content → no write. Event list puts return the semantic `added`/`removed` rows against everything the store knows in that range. Internal manifests are keyed by SHA-256 of the normalised unencoded report URL. Counts (`putCount`/`getCount`, `counts/pfun-<id>/<date>.json`) and ANPR (`putAnpr`/`getAnpr`, rows without the CSV `line`, issues in `adapter_stats.row_issues`) are stored too: every source of the build is in the store.
- `src/calendar/` (§6.4): pure `buildCalendar({ start, today, contributions })`, contributions built by `eventListContribution`, `internalEventsContribution` (r4–r6), `anprContributions`; regime boundaries and today are always added; `calendar.json` in the store keeps the sources of each date.
- `src/completeness/` (§6.5): `runSnapshots({ calendar, provider, anomalies, concurrency })` fetches every `(level, date)` of the calendar (memoised, bounded concurrency) and bisects each interval whose `S(d_i) ≠ S(d_{i+1} − 1)` (equality = manifest `content_hash`); inferred dates go into the global calendar (source `inferred`) and are verified for every level in later rounds. `storeSnapshotProvider` reads the store manifest first and fetches + stores only when missing or when `mustRefresh(level, date)`. Fetch failures become blocking anomalies by cause (`snapshot-unavailable` for network/5xx/429/open circuit, `snapshot-request-rejected` for non-retryable 4xx, `snapshot-schema-violation`, plus `completeness-unverified`), the run continues and the result is `blocked`; non-source errors propagate. Inferred dates carried over from `calendar.json` are dropped when no level changes on them any more (`info`); every inferred date left gets an `inferred-breakpoint` warning per changing level; `buildCalendar` drops `inferred` when a published event (public list or r4–r6) covers the date. `COD_PROV_STORICO` fallbacks become one `info` anomaly per level, from `adapter_stats`.
- `src/enrich/` (§6.8): `crawlInternal({ source, store, anomalies, concurrency, mustRefresh })` crawls r1/r2 → r4/r5 for every listed record → r7/r8 for every distinct event except `PV`/`CD`/`RN` (queried with the event row's own origin id and type), and r3 → r6 per pair (sorted; stored histories read first; pairs mentioned by a history are skipped), then r9 only for the ambiguous municipality events (same component, date and event code under several acts), used by the variation builder only to match public rows to acts by related code (golden-21, D37). With `offline: true` (offline `rebuild`) nothing is fetched: a report missing from the store is a failure of cause `unavailable`. `obtainInternalReport` is store-first; a mandatory refresh that fails for unavailability falls back to the stored copy (or the HTTP cache), never for validation errors or 4xx. A fresh history replaces the stored ones of the same ids (`preferFresh`). Anomalies are aggregated per report (`internal-data-stale`/`internal-data-unavailable` warnings, `internal-request-rejected`/`internal-schema-violation` blocking) plus `listed-record-without-events` per record. `summariseEventCodes`/`saveEventCodeSummary` write `<paths.reports>/event-codes.json` (never the store).
- `src/identity/identity-graph.ts` (§5.1): `buildIdentityGraph` is a pure union-find over the `id → id_origine` pointers only; components carry `root` (unique chain end, checked against the oldest record), `ids`, typed `records` and the merged, deduplicated `events` (sorted by date, then canonical JSON). Root or record inconsistencies are blocking anomalies.
- `src/identity/` (§6.7, Step 9): `resolveLevelIdentity({ level, index, internal, eventLists, anomalies })` builds the level's resolver (aliases from pfun 105 or `internalIdentity(graph, complete, view, source)`, plus the `typeChanges` of UTS/regions: a `CSCT` paired with the component member whose interval ends that day, whatever its events, D35; `type-change-unconfirmed` warning when neither an internal `ESCT` nor pfun 106/107/112/113 confirms it), runs `matchTransitions` (`transitions.ts`: links between snapshot intervals by code change, same code, cadastral fallback for municipalities; ends/starts from suppression/establishment events, only on dates where intervals open or close; chains) and `resolveEntities` (`entities.ts`: internal events give intervals their component root; chains cut on a root change, joined by root; `nk:` fallback keys and the per-level rootless rules). `registry.ts` (`Registry.load(dir)`, `assignEntities`/`assignVariations`, `entityId`/`variationId`, `save()`): entity ids are `<prefix>-<code>` strings, the code a 30-bit window of the SHA-256 of `<level>|<first natural key>` in Crockford base32 (`candidateEntityId`; the next window on a collision within the level, D42), stored and never recomputed; variation ids are integers; versions have no id and no registry (D40); remaps in `remaps.json` (`origin-id-available` not retroactive; `root-changed` retroactive); re-keying only `nk:` → `istat:`, never back: a registered `istat:` entity with no member in any entity of the run (its internal history is missing) is a `blocking` `internal-data-required`, never a new `nk:` id; every `internal-data-required` has `context.cause` (`InternalDataCause`: `unavailable` when an internal request of the level failed for unavailability, `NotInStoreError` included, else `absent`), computed per level in `commands/build.ts` and passed to `resolveLevelIdentity` and `assignEntities`; new ids follow a total order independent of the input (entities: first `validFrom`, first code, key; variations: date, key).
- `src/build/` (§6.9, Step 10): `buildRegionVersions` → `buildProvinceVersions` → `buildMunicipalityVersions` take `IdentifiedEntity`s (Step 9 entities + registry id) and return entities with half-open versions, which have no id: a version is `(entity id, validFrom)` (UTS also get `historicalCodes`). Region and UTS names with `/` come from the closed table of `bilingual-names.ts` (§4.2; checked against the decomposition rule when the module loads); one missing from it leaves the names null and is `bilingual-name-unknown` (blocking, with the suggested decomposition). Parents are entity ids from an `EntityTimeline` of the parent level (code → entity over time); versions merge contiguous pieces with equal published fields (canonical JSON). Pre-1948 UTS abbreviations come from `municipalityAbbreviations` (sweep over the municipality index, must be unanimous). An undetermined field is null internally plus a blocking anomaly (`version-parent-unresolved`, `abbreviation-underived`); I4/I8 report the null, I5/I7 skip it, the emitter refuses it. `timeline.ts` has the piecewise helpers (`cover`, `splitRange`, `mergeDated`).
- `src/build/` (§4.3, Step 11): `event-rules.ts` holds `EVENT_RULES`, the explicit rule of every `(level, event code)` pair (effect, sides of subject and related territory, flow direction; D27); `checkEventRules(summary)` makes every observed pair without a rule `blocking`. `buildVariations({ levels, start, inferredDates, anomalies })` (`variations.ts`) turns public rows (resolved with the level's resolver) and internal events (`internalVariationEvents(crawl)`, entity by component root) into facts, matches rows to internal events by `(date, entity, event)` (then, without an exact match, by an equivalent code of the closed `EVENT_CODE_EQUIVALENCES`, only when unique, else `blocking` `event-code-equivalence-ambiguous`; the variation keeps the public code, one aggregated `event-code-mismatch` info, D48), groups them (`act:<act>:<date>` across levels; rows without act by connected components, `nk:<date>:<level>:<min entity>`, never merged into act groups; a row without act whose links all exist in a fact with an act is accounted to that act's variation instead, one aggregated `link-explained-by-act` info, D43), participants reference versions by `validFrom` (`versionBefore`/`versionAfter`), evaluates the effect **per event** (no-effect rows dropped with `info`), derives roles, links (kind from the effect) and covers the remaining boundaries (`indirect` in the parent's variation, `inferred` only for upstream warnings, else `version-boundary-unexplained`). Territorial events fall back to `date − 1` (ceded the same day, D33). A UTS boundary with only the abbreviation changed gets an `inferred` variation and `abbreviation-change-without-event` (D34); an establishment whose associated territory is the subject itself is ignored (one aggregated `self-reference-ignored` info, golden-20). Name changes along type-change links are not `name-change-without-event` (§6.7). Events dated after `today` (an option) are dropped as `future` (one aggregated `future-event-ignored` info, D49) before anything else. It returns drafts plus `accounts` (one per row: variation key or drop reason, I14); `registerVariations` assigns ids. `CT` (§3.5 item 18) is an internal-only event code.
- `src/overrides/` (§6.10, Step 12): `loadOverrides(dir)` reads every `*.json` of `overrides/` (zod schema in `schema.ts`, closed set of fields discriminated by `field`: only the UTS `abbreviation` for now; inclusive `date_to` converted to half-open); invalid files, duplicate keys or overlapping overrides of the same field and code throw `OverrideFileError`. `OverrideRun` (`apply.ts`) is passed to `buildProvinceVersions`, which applies the overrides to the values of every day **before** the merge (D36): they may remove version boundaries, never create one (`override-creates-boundary`, blocking); `run.finish(anomalies)` reports `override-obsolete` (no day matched, or every matched day already had the value) and returns the `AppliedOverride`s (days replaced, used by I12).
- `src/crosscheck/` (§6.11, Step 14): `loadAnpr({ source, anomalies })` returns the ANPR rows (with `fetchedAt`) or `null` (any `AnprFormatError`/`HttpClientError`/`ResponseValidationError` → one `anpr-unavailable` warning; other errors propagate; dropped rows → one `info`). `crossCheckAnpr({ anpr: { rows }, municipalities, provinces, today, anomalies })` runs after the derived fields, only up to `today` (rows starting later ignored, rows ending later open; anomalies keep the stored row, D49), on `AnprRecord`s (the stored rows, no CSV line: sorted with `compareAnprRecords`, identified in anomalies by their store row hash plus `{ istatCode, cadastralCode, validFrom, validTo }`): join by cadastral code when both sides have one, else by ISTAT code (a version or an ANPR row without cadastral code); a stretch of ANPR rows matching no version is retried by ISTAT code, and the cadastral code is then compared with the history rule (`anpr-divergent-cadastral` warning, `anpr-lagging-cadastral`/`anpr-anachronistic-cadastral` info) (`matchedBy` per pair); consecutive rows compared day by day, only the days where rows of the join key overlap → `anpr-not-comparable`; names compared in uppercase against official or Italian name (equal without diacritics → `info`), provinces against the province's historical code; a different ISTAT code, province or name of an earlier time of the municipality → `info` lag, of a later time → `info` anachronism, never in its history → `warning`; dates by direction: ANPR covering less → `anpr-missing-period` (info), more → `anpr-unmatched-period` (warning) unless a known case (`info`, in this order: `anpr-anachronistic-key` (the municipality exists then under another key), `anpr-cession-extended` (after the last version of a former Italian entity), `anpr-boundary-offset` (≤ 365 days next to an establishment/reconstitution or suppression)); missing `EX` on a former Italian entity → `info`, `EX` on one that is not → `warning`. Never blocking: warnings one per divergence, info one per code with `{ count, items }` (codes in `anomalies.ts`).
- `src/invariants/` (§8.1, Step 15): one independent check per invariant (`checkI1`…`checkI15`, grouped in files by topic), each returning its violations as `blocking` anomalies `invariant-i<n>` with `context.invariant`; plus `checkActive8xxCodes` (D30 `warning`). They run on the internal model (`InvariantWorld`: derived entities per level, variations, `start`/`today`). `checkInvariants(world, anomalies?, { now? })` runs them all (with `now`, each result gets `durationMs`) and returns a result per invariant (`passed`/`failed`/`skipped` with reason): an invariant whose optional data is missing from the world (I2 `existence`, I7 `historicalCodes`, I12 `snapshots`+`overrides`, I13 `counts`, I14 `accounts`+`variationIdOf`) is `skipped`, never passed. `assertInvariants(report)` throws `InvariantViolation`. I11 recomputes the derived fields with `deriveFields`; I12 (`checkI12Detailed` also counts the pre-1948 abbreviations it could not compare, exposed as `uncompared` in the result) streams `SnapshotSet`s (`storeSnapshotSets(store)` for the stored ones) and compares each version's projection on each date, with the per-version expected abbreviation (override → snapshot value → pre-1948 derivation from the municipality rows with the builder's own function). I7's "UTS codes of some time" are those of the checked world only (UTS versions and their historical codes); `extraUtsCodes` is a test-only parameter for partial worlds.
- `src/derive/` (§7, Step 13): `deriveFields({ level, entities, variations, anomalies })` adds `status`, `predecessors`/`successors` (links taken **by date** from every variation dated on the first `validFrom` / last `validTo`, whatever act references the boundary; `transferred_to` excluded, joined, deduplicated by `(id, kind, date)`, sorted by id, kind; a `merged_into` of one origin towards several destinations on one date becomes `split_into`, D44; successors only for suppressed entities), `currentSuccessors` (municipalities only, closure over `merged_into`/`split_into`/`detached_into` to active entities; `null` for regions and provinces, which are resolved through the municipalities, D46) and `isFormerItalian` (ceased because ceded abroad: closed with `ceded`, read from the participants referencing the last version, is terminal, D33; otherwise every successor path must end in a ceded entity; not a measure of lost territory). The resolution to the current territory (§7, D45: automatic only with one current successor and no former Italian successor, direct or indirect) is a rule on the public data, not a field: `test/helpers/resolution.ts` implements it for the tests (golden-22). A cycle among final closures is a `blocking` `successor-cycle` (one per strongly connected component); consistency is I11 (Step 15).
- `src/emit/` (§6.12, §9, Step 16): `emitDataset({ dirs: { dist, reports }, world, anomalies, previous, generatedAt, today, sources })` writes the public files and their schemas to `dist/` (`toPublicData`; entities in `comparePublicOrder`: by internal ISTAT root numerically, `nk:` entities last by first `validFrom` then id, presentation only) and the internal reports to `reports/` (`toReportVariations`, `toReportAnomalies`, changes, meta), validating every file with its model (`parseReleaseFile`; `EmitError` otherwise, also for null undetermined fields and blocking anomalies). The release kind is decided by the public files only: `unchanged` (public data files and schemas equal to the previous release: nothing written, reports included), `schemas` (same data, new schemas: `schema/*`, empty `reports/changes.json`, the previous `reports/meta.json` with only `schema_version` and `generated_at` changed), `data` (every file); `reports/meta.json` is always written last. `computeChanges` (entities by id, versions by `(entity_id, valid_from)`, variations by id; retroactive = changes a day before the previous `data_version`; `affected_from` on updated/removed items), `sourceSummaries(store)` (per §6.1 family, all from the store: counts in `situas-public-reports`, the stored ANPR archive), `loadPublishedDataset({ dist, reports })`, `toInternalData` (release → internal, for `validate`). `generatedAt` and `previous` are inputs: the emitter reads neither the clock nor git.
- `src/resolve/` (§6.6): `loadIntervalIndex(store, level, calendarDates, anomalies)` builds an `IntervalIndex` (code → maximal `[validFrom, validTo)` intervals of the same row hash; the last calendar date is open; a code duplicated in one snapshot → `snapshot-duplicate-code`, left out of that date). `CodeResolver.resolve({ level, code, date, side, cadastralCode? })` returns `{ intervalKey: "<code>@<validFrom>", interval, path }`: a snapshot interval, never an entity (Step 9 maps them). Order: direct on `date` (successor) or `date − 1` (predecessor), same-day aliases of `date` (chains, towards the side), cadastral code (municipalities only); not found or ambiguous → `ResolutionError`, `resolveOrReport` turns it into `code-unresolved` (blocking). Aliases: `municipalityAliases` (pfun 105: `code` = code of `D − 1`, `related.code` = code of `D`) and `internalAliases(graph, view, source)` (UTS/regions: `RN` old code from the same record's last earlier event; `ESCT` ↔ `CSCT` codes of a component on the same day).
- `src/commands/` (§10.1–§10.2, Step 17): `runPipeline(ctx, mode)` (`bootstrap` | `update` | `rebuild` | `rebuild-refetch`; offline `rebuild` requires an offline `RunContext`, whose client transport is `offlineTransport`: every request throws `OfflineRequestError`, a programming error; offline stages read only the store and a missing source throws `NotInStoreError`, classified `unavailable`): `acquire.ts` (event lists, internal crawl with the mandatory refreshes of the mode, ANPR, counts; stored, then read back) → calendar (with the `inferred` dates of `calendar.json`) → `runAudit` (update) → `refreshStoredSnapshots` (bounded concurrency; update: from late events / audit corrections to the previous today, within `update.maxRefreshSnapshots`, else `refresh-too-large`; `rebuild --refetch`: all). Mandatory refreshes use `refreshPolicy(mode, today)`: `refresh`, or `{ fetchedSince: today }` in `rebuild --refetch`, so an interrupted refetch resumes the same day without sending a request twice → `runSnapshots` → `buildDataset` (`build.ts`, no network: identity → versions → variations → overrides → derived fields → ANPR → invariants) → `emitDataset` + `registry.save()` only without blocking anomalies. `exitCodeOf` maps anomaly codes (`*-unavailable` and `internal-data-required` with `cause: unavailable` alone → 3, other blocking → 1, retroactive → 2). `runDataCommand` always writes the run summary (`paths.runSummary`, `.cache/last-run.json`, zod model in `summary.ts`, with `last_complete_update`: a pipeline command ended with exit 0 or 2 records its `today` in `last-complete-update.json` of the store, never moving it back, `complete-update.ts`), also on SIGINT/SIGTERM (`interrupted`, exit 130/143) and on uncaught exceptions through `runtime.process` (tests use `fakeProcess()`), and logs the blocking anomalies and the requests refused by disabled endpoints (`HttpClient.disabledEndpoints()`). The release lives in `paths.dist` and `paths.releaseReports` (`releaseDirs(ctx)`). `runAuditCommand`, `runValidate` (`dist/` + `reports/variations.json`; I2/I7/I12/I13/I14 skipped), `runDiff` (two directories, each holding `dist/` and `reports/`). The run summary also counts the `split_into` links per level (`derived`). `RunContext` (`context.ts`) holds config, today, logger, runtime, store, sources, anomalies and the summary builder; `timed()` records stage timings.
- Release and workflows (§9, §10.3, Step 18, D47): `scripts/release.ts` (`changelog`, `check`, `version`, `notes`, `pack <dir>`; version `MAJOR.YYYYMMDD.PATCH` from the first CHANGELOG entry, which records `schema_version`/`data_version`/`generated_at` in a `<!-- release {...} -->` comment; `pack` stages the npm package: the six published files of `dist/`, the TypeScript declarations generated from the schemas by `src/model/typescript.ts` (`types/<file>.d.mts`/`.d.cts`, never committed), README, data licence and a `package.json` with explicit `exports`; no executable code; the root `package.json` stays private). The store lives in the separate repository `italian-territories-store` (`.github/actions/store`: shallow clone into `.cache/store`, commit and push with the `STORE_DEPLOY_KEY` deploy key). `weekly-update.yml` (`update`) and `rebuild.yml` (offline `rebuild` only) end with `.github/actions/data-output` (only a changed `dist/` is delivered, `release -- target`: changelog + check, then commit to `main` and `gh workflow run release.yml -f sha=…`, or the single `data-update` PR, always while it is open) and `.github/actions/data-verdict` (exit 1 fails; 3 warns, fails when `last_complete_update` is over 21 days old). `release.yml` is the only release entry point (push to `main` on `dist/**` or `workflow_dispatch`; npm trusted publishing; idempotent tag `v<version>`, GitHub Release, publish). `rebuild --refetch` and `bootstrap` run only locally (procedure in Step 18).
- `src/anomalies.ts` (`AnomalyCollector`, anomalies are data) and `src/logger.ts` (NDJSON on stderr, `--verbose` enables `debug`; `logHttpEvents` maps the client's `onEvent`, one `http endpoint disabled` line per disabled endpoint; `time`/`level`/`msg` are reserved and forbidden in `LogFields`: log a territorial level as `territoryLevel`). The CLI passes `ctx.logger` to commands. `src/progress.ts`: `stageProgress` (`add`/`done` counters, a `progress` line every 30 s from an injectable `Scheduler`); `timed(ctx, name, (progress) => …)` creates one per stage.
- `src/dates/`: all date handling goes through it. `calendar-date.ts` (ISO validation, day-number arithmetic, `DD/MM/YYYY` and `…T00:00:00Z` source formats, `currentDate()` in Europe/Rome, the only place a `Date` is read) and `interval.ts` (`HalfOpenInterval` internal ↔ `InclusiveInterval` public, membership, overlap, coverage, contiguity).
- `src/model/`: `common.ts` holds the shared vocabulary (levels, event codes, types, roles, code patterns, `PARTICIPANT_ROLE_RULES`), with each `as const` list feeding both the TS union and the zod enum. `internal.ts` has the camelCase pipeline types (snapshot projections, entities/versions with half-open intervals, variations whose `role: null` means no-effect). `public.ts` has the strict zod models of the three published files (snake_case, keys in published order, string entity ids, versions without id, per-record checks only; cross-record rules belong to the invariants); `reports.ts` those of the internal reports (variations, anomalies, changes, meta). `json-schema.ts` generates `dist/schema/*.schema.json` for the public files only; `typescript.ts` turns those schemas into the package's type declarations (unknown schema constructs throw; `test/unit/type-declarations.test.ts` checks them equal to the zod models).

## Test fixtures (§11.1)

- `test/fixtures/` holds real SITUAS/ANPR responses at a path **derived from the request**; each file has exactly one entry in `test/fixtures/manifest.json` (`used_by` must reference a golden case `golden-<n>` of §11 or a quirk `quirk-<n>` of §3.5).
- `test/helpers/fixtures.ts`: `fixturePath`/`describeRequest` (request → path/source/endpoint), the manifest zod schema, and `createFixtureTransport()`, which serves only `full` fixtures and throws on anything unknown.
- `test/helpers/json-schema.ts` (`publishedSchemaViolations(dir)`): validates a published directory against the JSON Schemas it publishes with Ajv (dev dependency, tests only, never in `src/`).
- `test/helpers/world.ts`: a declarative world (Veneto and Sardinia from 2000-01-01) and a transport answering every request of a run in the raw source formats (checked against fixture rows by `test/unit/world-formats.test.ts`); `test/helpers/commands.ts` (`sandbox(world)`) runs the real CLI on temporary paths. `test/e2e/commands.test.ts` changes the world between runs for the Step 17 scenarios.
- `test/unit/fixtures-manifest.test.ts` enforces these rules (including parsing the plan to check `used_by`). Adding a fixture means adding its manifest entry with the conventional path; subsets are named `<base>__subset-<description>.<ext>` and must never be treated as complete.
